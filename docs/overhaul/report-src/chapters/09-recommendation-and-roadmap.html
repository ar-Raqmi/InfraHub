FINDINGS-bq “Recommendation” · steps and sizes Inference

Why B

  • It matches the real object. One sebutharga has one Jadual Kadar Harga, and the data already behaves that way: one rate per item for everyone, one sebutharga number per year.
  • It fixes all four situations: a new year, two contracts at once, a straddling project, a pelarasan after the contract ends. The editors already take “a library” as input; only which library changes.
  • No project is rewritten. 99.76% agreement and reconciling cost columns say the stored copies should be left alone.
  • Stable ids give most of Option C’s benefit and make a later move to C a data conversion, not a redesign.

Settle these too

  • Lock the contract BQ once the inden exists. 4 + 7 rows show contract BQs edited after pelarasan began.
  • Record when a rate was typed by hand. 20 rows differ today and the cause is unknown.
  • Move the meeting number and date from the year to the contract.
  • Option D only if you confirm rates change inside a contract period.

If the next contract arrives before anything is built

The safe manual routine

  1. Export the Pustaka to Excel first and file it as the old schedule.
  2. Finish adding items and pelarasan additions on old-contract projects where possible.
  3. Only then change the rates in the Pustaka.
  4. Treat any later addition to an old-contract project as a hand-typed rate that must be checked against the filed schedule.
