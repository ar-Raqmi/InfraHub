The pipeline

Six statuses, moved by four fields

A project’s status is a stored label, not a process engine. Typing a company name or one of three dates moves it forward. Only the very first step needs a person to change it by hand.

Rules fire only in the form

The automatic moves run when a field changes in the project form. Values set by Import Inden or the card’s quick-edit bypass them. Clearing a date never moves the status back. Verified

Nothing remembers who or when

There is no history table. The only trace is one updated_at per project, so “who moved this, and when?” cannot be answered. The date fields are the only clock. Verified

Three roles

PJA (12): build the BQ and the pelarasan. ADMIN / PT (2): open the file, appoint, close. JURUTERA (2): sign letters and certificates. PJAs see only their own projects. Verified

A trap in the code: choosing or editing Nama Syarikat sets DALAM_PROSES even on a project that is already SIAP. No project in the data shows it, but nothing prevents it. Inference from code reading

The data mostly agrees with the rules

1 SIAP project has no Tarikh Padanan; no project has a Padanan date outside SIAP; 2 projects hold a Tuntutan date while still in an earlier status. In 275 of 293 finished projects Tarikh Pemeriksaan equals Tarikh Siap Sebenar: one event typed twice. Verified

The notice tracker is used for the exceptions

Peringatan 1 is SENT on 66 projects (52 of them now SIAP), Perakuan Kerja Tidak Siap on 28, Peringatan 2 on 22, Peringatan 3 on 15. Most projects leave all four at PENDING (417, 447, 466 and 472 projects); 3 are marked “Tiada notis diperlukan”. Verified
