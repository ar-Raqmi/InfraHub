UI/UX · choosing

No direction wins everything

Each of A, B and C is best for one group of users. They share one contract model, so the strongest answer is to merge their best parts.

The suggested merge

A’s pipeline as the home, B’s BQ sheet and contract register on the desk, C’s measuring flow on the phone, all on one contract and rate-book model. Inference

From A · Saluran

Home: the pipeline

Six statuses with stage ages and a contract chip on every card; the project page repeats the steps.

From B · Lejar

Desk: BQ sheet and contract register

Every rate shows its source and history; contracts are dated records with a version diff.

From C · Tapak

Phone: measure on site

Big steps, a keypad, an offline queue; a rate change arrives as a two-choice sheet.

One contract model under all three

data · needed by any choice

  1. A contract record per sebutharga: number, rate book, valid from–to, draf / aktif / ditutup.
  2. Rate-book versions; “Klon kontrak” copies one into a new draft contract.
  3. Each project bound to a contract, version and lock date; each item keeps its contract rate and the kekal / baharu decision.
  4. A comparison step that feeds A’s queue, B’s diff column and C’s bottom sheet.

Four UI decisions for you

  1. Which base? A, B, C, or the merge above. It sets which screens are built first.
  2. Phone flow in release one? The offline queue is the largest single step (about 2–3 weeks of C’s 8–11, estimate).
  3. Who makes the rate choice? The PT alone in a queue (A, B), or the PJA proposes and the PT confirms (C).
  4. One visual system? One type family with real numerals, MPS purple only for contract things, Malay-only labels (audit 13–15).
